# Supabase auth email templates

The six emails Supabase sends on our behalf — signup confirmation, password
reset, magic link, email change, invite, reauthentication. They are **not** sent
by `src/lib/email.ts`, so nothing in this repo controls them. They live in the
Supabase dashboard and have to be pasted in by hand.

Supabase dashboard → **Authentication → Emails → Templates**.

> **This file is the only copy of these templates.** The dashboard has no
> export, no version history and no backup — what is pasted into it is not
> stored anywhere else. Recreate the project, reset a template by accident, or
> migrate to another Supabase org, and this file is what you paste back from.
> Edit here first, then paste; never the other way round, or the two drift and
> the dashboard copy silently wins.

## Still open

Only one thing, and it is not a template setting:

- [ ] **The grey circle beside the sender name in Gmail.** That is BIMI, not
      anything in the HTML below. It needs DMARC at `p=quarantine` or
      `p=reject` — we are at `p=none` until about 29 Aug 2026 — **and** a paid
      Verified Mark Certificate, which requires a registered trademark. See
      [About the logo](#about-the-logo). The logo *inside* the message body
      renders correctly today; these are different things and get confused
      constantly.

Everything else is done. **Verified end to end on 15 August 2026** on the
Cloudflare deployment: SMTP through Resend, Site URL and the `/auth/callback`
redirect, `logo-email.png` serving, and real delivery — a password reset arrived
in the Gmail inbox rather than spam, from `noreply@outway.club`, with the logo
rendering, **SPF, DKIM and DMARC all PASS**, and the link resolving to
`outway.club` rather than `localhost:3000`. The full checklist is at
[Verifying](#verifying).

## Two settings, two different problems

People conflate these constantly, so, plainly:

| Problem | Where it is fixed |
|---|---|
| Mail arrives from `noreply@mail.app.supabase.io`, not from us | **SMTP Settings** — sender identity |
| Mail arrives from us but looks like a system alert with no logo | **Templates**, below — the message body |

Setting SMTP does not restyle the email. Pasting a template does not change the
sender. You need both.

### The SMTP half

Project Settings → **Authentication → SMTP Settings**:

| Field | Value |
|---|---|
| Host | `smtp.resend.com` |
| Port | `465` |
| Username | `resend` |
| Password | your `RESEND_API_KEY` |
| Sender email | `noreply@outway.club` |
| Sender name | `Outway Club` |

The DNS side of this is already live and verified — SPF, DMARC, both DKIM keys
and the Zoho/Resend MX split are all in place (see
[`infrastructure.md`](infrastructure.md)). Nothing to add — and note that DNS
now lives at Cloudflare, not Porkbun.

> **The built-in sender is not a production option.** Supabase rate-limits it to
> a handful of messages an hour and says so in their own docs. On a launch day
> where twenty people sign up, most of them silently never receive a
> confirmation link.

## About the logo

Three separate things get called "the logo", and only the second one is what
these templates control.

**1. The logo inside the email body.** What the templates below add. It has to
be an `<img>` pointing at a publicly reachable absolute URL — email clients
cannot see your project, your CSS, or anything on Zoho. These use
`https://outway.club/brand/logo-email.png`, which is generated by
`scripts/build-brand-assets.mjs` at 144px and 9.5KB.

Do **not** swap it for `/brand/logo.png`: that one is 167KB, and Gmail clips a
message at roughly 102KB, hiding everything past the cut behind "View entire
message" — including your button.

**2. The avatar beside the sender name in Gmail.** Not controlled by the email
at all. That circle comes from BIMI, which needs DMARC at `p=quarantine` or
`p=reject` (we are at `p=none` today) **plus** a Verified Mark Certificate — a
paid certificate that requires a registered trademark. It is a real thing worth
doing eventually; it is not a template setting, and it is not quick.

**3. The logo uploaded in Zoho Mail.** This is the one that will not do what you
want. Zoho's organisation logo brands *Zoho's own webmail interface* — what you
see when you log in to read mail. It is never attached to outbound messages, and
it has no effect whatsoever on mail that Supabase and Resend send, which never
touches Zoho. That upload is not broken; it is simply for something else.

## Rules that outlive the initial setup

These apply every time one of these templates is touched, not just the first
time:

- **Site URL** must stay `https://outway.club`, with
  `https://outway.club/auth/callback` under **Redirect URLs** (Authentication →
  URL Configuration). If either is wrong, every link below resolves to
  `localhost:3000` and lands in a dead end for everyone who is not you.
- `{{ .ConfirmationURL }}` is filled in by Supabase. Leave it exactly as
  written, braces and spaces included.
- Subject lines are set in the field above the body, not in the HTML.
- **Minimum interval per user** is 60 seconds. A second mail to the same address
  inside that window is dropped without an error — which looks exactly like a
  delivery failure when you are testing. Wait a minute between attempts, or test
  with different addresses.
- The dashboard preview pane does not render like Gmail. Send a real message.

## Verifying

Configuration being right and mail actually arriving are different claims, and
only the first can be checked from a dashboard. Run this after any change to
SMTP, DNS, or the templates themselves.

**All five passed on 15 August 2026**, on Cloudflare, against a real Gmail
account:

- [x] Mail arrives, logo renders, button works
- [x] Password reset — same
- [x] Gmail → **⋮ → Show original** shows SPF, DKIM and DMARC all `PASS`
- [x] Neither mail landed in spam
- [x] The link lands on `outway.club`, not `localhost:3000`

One thing that is **not** a failure, and looked like one during that test:
opening a reset link in a different browser from the one that requested it
gives "Open the reset link in the same browser you requested it from". That is
PKCE working as designed — the code verifier lives in the requesting browser —
and the app catches it with a readable message rather than a dead end.

Settled and worth not re-litigating: SMTP sender identity, Site URL and
redirect, the logo asset being deployed, and delivery itself.

### When the logo shows as a broken image

Open `https://outway.club/brand/logo-email.png` in a browser first — that one
check separates the two causes, and they have nothing to do with each other.

**It 404s.** The asset ships from `public/brand/`, so it only exists on a deploy
that includes it. It is generated by `scripts/build-brand-assets.mjs`, which
means it can be regenerated locally and then *not committed* — the file sits in
your working tree looking present while production has never seen it. This
happened once already. Check `git status` before assuming the template is wrong.

This is also why the templates hard-code the apex domain rather than a preview
